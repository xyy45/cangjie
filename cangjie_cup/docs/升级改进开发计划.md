## 第1阶段设计

### 接口和行为

上传时可选填写/导入独立规则JSON；确认函数和公开示例时，一并确认规则。未填写时保持原模式，不声称自动推断未覆盖语义。规则与原始源码、确认版本及冻结工程绑定，后续候选不能修改。

规则契约v1包含函数、参数域（Int64或Bool，整数上下界及临界点）、返回值表达式、随机种子和有限搜索预算。表达式仅允许参数、整数/布尔、受限算术比较和条件、min/max/ceil_div；使用白名单语法树解释器，禁止eval/exec、成员、导入、下标和任意调用。所有中间整数遵循Int64范围约束，不支持的或未定义的规则拒绝确认/停止验证。公开例子必须与规则一致。

固定算法版本、种子与契约生成临界值邻近、参数组合及随机输入。数量有上限，不宣称穷尽所有输入。普通工程测试PASS后，再执行独立搜索；二者结果分别保留。没有规则不执行搜索。

验证在服务持有的独立临时工程中执行，不修改候选/原冻结测试；使用同一仓颉工具链和沙箱。失败后进行预算受限的缩减，只保留经实际执行确认仍失败的输入；不承诺全局最小。将输入、预期、实际、规则摘要、候选树摘要、原始日志及搜索预算记录为独立证据。

搜索FAIL驱动后续候选，UNKNOWN/超时阻止进入可接受状态；累计反例优先回归。只有普通测试及当前版本独立搜索都PASS才允许人工接受与交付。交付时复核证据绑定，不因页面状态或循环结束而绕过门禁。

### 方案选择

采用确认规则契约与有限搜索，复用现有循环/验证器/沙箱/SQLite。没有独立规则依据时不能从自然语言或修复模型输出猜测正确答案。后续可增加可信参考程序、属性规则及求解器，但不能将这些尚未实现的能力写成当前支持。

### 当前边界

上传仍保留现有Int64/Bool语言子集。第1阶段不改为通用仓颉工程；不替换现有策略边界。已有记录与旧验证计划保持可读，功能默认关闭。真实付费模型联调与确定性模型夹具的结果明确区分。

## 验证与完成规则

每阶段执行专项单测、相关集成、全量离线Python与Node测试、必要浏览器检查。第1阶段必须包含真实SDK用例：首轮公开测试PASS但规则搜索FAIL，第二轮满足公开测试和累积反例；模型HTTP夹具只验证集成，不能称为真实DeepSeek能力证据。

常规命令（在CangSight-Nexus-Demo下）：
- `../.venv/bin/python -m pytest tests -m 'not live' -q --tb=short`
- `node --test tests/*.test.cjs`
- `git diff --check`

证据需包含实际命令、退出状态、测试数量及未验证限制。不能沿用上一版本绿色结果。失败恢复、超时、非法/矛盾规则、候选及证据篡改属于必要测试。
