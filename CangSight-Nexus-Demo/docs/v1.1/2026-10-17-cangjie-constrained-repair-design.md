## 1. 项目概览

### 1.1 项目要解决的实际问题

用户提出的定位是：

> 面向仓颉工程中需求理解、候选修复、工程验证和结果追溯相互割裂的问题，在 Sympas-Nexus 既有编排、网关和事件存储基础上，构建受约束的代码修复系统。

**[设计] 产品定义：** 开发者选择一个已登记的小型仓颉工程，确认修复需求及验收条件；系统经 MCP 诊断源码，调用模型生成有限修改，在独立候选中运行真实构建和测试；失败时提供带代码上下文的反馈；通过后由用户审阅，导出与检查结果对应的工程。

系统连接的不是四个独立页面，而是同一条任务链：**一项需求对应哪些修改、哪些测试验证了它、失败如何影响下一稿、最后下载的是否正是接受的版本。**

**[推断] 目前更准确的定位是“核心流程已有实现的受控仓颉修复 MVP”，不是已经完成上述所有连接的系统。** 这一判断依据上表，不以界面、工具数量或代码行数衡量完成度。

### 1.3 首版范围与非目标

**[设计] 首版支持范围：**

- 本机、单用户、一次一个执行中的修复任务；多个历史任务可查询。
- 先支持维护者登记的自产仓颉小工程；可配置登记目录，但不开放任意上传工程自动执行。
- 沿用现有入口限制：每工程最多 100 个纳入快照的文件、2 MiB；每候选修改 1–3 个既有业务 `.cj` 文件，不新增依赖、不改测试和构建配置。[S2](#s2)
- 必需范围是一个完整主案例 A 和一个真实拒绝场景 D；跨文件案例和额外的退化修复演示属于主链稳定后的增强项。
- 使用真实 MCP、真实仓颉策略和真实构建测试；不要求课题组所有工具支持仓颉。

**[设计] 截止前不做：** 任意来源项目的安全执行、完整仓颉 AST／调用图前端、多 Agent 自由协作、Docker／云部署、Redis／消息队列、自动生成复杂测试平台、通用形式化证明、IDE 插件。

限制规模是交付边界，不意味着系统可以预造候选、固定模型回答或伪造通过状态。

| 层次 | 技术与首版选择 | 为什么使用 | 边界 |
| --- | --- | --- | --- |

| 网关与页面 | Flask／Jinja／原生 JavaScript | [事实] 交付包已有完整入口。[S7](#s7) [设计] 最少改动即可接入新需求卡与运行视图 | 保持 loopback、本地会话和 CSRF 保护；不是公网服务 |

**[设计] 准确版本原则：** 以交付基线的锁文件和正式主机实测为起点；只有兼容问题确实需要时才升级，升级后重跑协议与回归。本文不要求立即配置任何环境。

## 4. 核心知识点与数据设计

### 4.1 四个问题，用同一组对象连接

| 对象 | 最少字段 | 责任方 |
| --- | --- | --- |
| `RequirementSpec`（新增） | `id, version, source_text, requirements, allowed_paths, confirmed_by, spec_hash`；各需求保存可观察行为、保持项与不覆盖条件 | 用户确认；服务端校验并计算摘要 |
| `VerificationPlan`（新增） | `id, version, baseline_hash, spec_hash, toolchain_id, required_suites, requirement_test_map, context_visibility, plan_hash` | 维护者提供受控测试和可见性，服务端冻结 |
| `TaskRecord`（扩展） | 现有字段＋`revision, spec_id, spec_hash, verification_plan_id, verification_plan_hash, runtime_binding, allowed_tools, budget` | 任务服务／唯一状态存储，`revision` 用于状态比较更新 |
| `ToolRequest`（逻辑契约） | `request_id, task_id, candidate_id?, tool, tool_version, arguments, input_tree_hash, deadline_at` | 控制层补齐并由 MCP Server 校验 |
| `PolicyDecision`（逻辑契约） | `request_id, arguments_hash, input_tree_hash, policy_version, policy_component_hash, decision, reason, approval_binding?` | 仓颉实际决定，可信调用侧补齐组件身份与绑定 |
| `CandidateProposal`（扩展） | 现有 `edits, requirement_refs`；增加引用有效性校验 | 模型提出，服务端不信任其声明 |
| `CandidateRecord`（扩展） | 现有字段＋`spec_hash, verification_plan_hash, model_call_id` | 候选服务生成，不由模型指定 |
| `CheckResult`（扩展） | 现有结果＋`argv, working_root, toolchain_hash, duration_ms, report_ref, suite_results, limitations` | 固定验证器记录真实执行；测试投影区分目标行为和回归 |
| `RepairFeedback`（新增） | `previous_candidate_id, tree_hash, diff, edited_files, failed_checks, diagnostic_snippets, remaining_budget` | 控制层从失败候选与真实结果构造 |
| `ReviewRecord`（新增） | `candidate_id, spec_hash, requirement_results, check_set_hash, decision, decision_source, actor_id, reason` | 评审服务汇总；用户接受／拒绝单独记录来源 |
| `RunEvent`（新增统一契约） | `event_id, task_id, sequence, type, candidate_id?, input_ref?, output_ref?, object_ref?, status, occurred_at` | 唯一事件存储，按任务顺序追加 |
| `AcceptanceRecord`（扩展） | 现有绑定＋`actor_id, allowed_actions, status, consumed_by_export_id?, consumed_at?`；同时绑定需求和验证计划摘要 | 服务端从本地用户会话取得身份，维护审批消费状态 |

**[设计] 不为每个对象单建微服务。** 数据先保持在现有应用内；对象身份由服务端生成，模型只输出修改和解释。JSON 中的版本与 ID 不能被模型用来改变批准范围。

上述持久化记录和跨进程消息均带 `schema_version`；它与需求内容修订的 `version` 分开。未知协议版本、非法字段或不兼容旧记录明确拒绝；需要读取历史记录时使用显式兼容转换，不静默猜测缺失权限字段。约束中的逻辑 `TaskSpec` 由 `TaskRecord + RequirementSpec + VerificationPlan` 共同表达，不要求为同一任务另建第二份状态对象。

内容摘要规则固定为：规范化相对路径 → 文件字节摘要 → 按路径排序的规范清单 → 总树摘要。清单覆盖影响工程行为的源码、测试与配置；`target/`、`.git/` 等排除项由登记 profile 明确记录，SDK、密钥和运行库放在工程外。首版拒绝符号链接及未登记文件类型；文件权限等影响执行的元数据应按登记规则规范化并核验，无法规范化则拒绝，不宣称仅内容摘要已覆盖这些元数据。工具链与策略组件身份另外记录。

### 4.2 需求卡不是让模型“再说一遍需求”

以订单案例为例，以下为**目标结构示例，不是当前已存在的记录**：

```json
{
  "schema_version": 1,
  "id": "spec-order-v1",
  "version": 1,
  "source_text": "修复订单数量边界，保留价格校验与总额计算",
  "requirements": [
    {"id": "REQ-QTY", "text": "数量为 1–1000，边界包含 1 和 1000"},
    {"id": "REQ-PRICE", "text": "单价为 0–1000000，非法订单返回 -1"},
    {"id": "REQ-TOTAL", "text": "合法订单总额为数量乘单价"}
  ],
  "allowed_paths": ["src/quantity.cj", "src/fee.cj", "src/order.cj"],
  "confirmed_by": "local-user"
}
```

用户看到三条简短业务条件，可以确认或修改。服务端再冻结 `spec_hash`，并从本地用户会话取得 `confirmed_by`；示例中的身份值是说明，不接受模型或客户端自行声明可信审批身份。存在歧义时返回待确认，不默默选择一种业务解释。

**[设计] 首版采用已有样例的结构化模板＋人工确认，不增加必需的模型调用。** 后续可允许模型把自由文本整理为草稿，但必须经过用户确认；这次辅助调用单独计入预算，不能混进“三候选”次数里。

### 4.3 需求—测试—结果映射

| 需求 | 需要的测试类别 | 结果解释 |
| --- | --- | --- |
| `REQ-QTY` | 0、1、1000、1001；负数 | 实际执行且通过，才支持数量范围这一条需求 |
| `REQ-PRICE` | 负单价、0、上界、超上界 | 不能因数量测试通过就推断价格正确 |
| `REQ-TOTAL` | 多组合法输入、零价格、组合边界 | 用于发现删除计算逻辑或返回常量等退化修改 |

**首版最小实现：** 维护者在登记 profile 中预先配置需求 ID、目标行为测试套件和回归套件的对应关系。允许采用固定样例的套件级映射，不要求建设通用测试发现、逐断言解析或自动覆盖分析平台。

测试名称与日志格式按实际仓颉输出核对。验证器依据冻结的测试集合和可核对的完整报告判断目标行为／回归结果；有可靠用例项时再做更细投影。若只有总数、无法确认对应集合实际执行情况，则相关需求级结果为 `UNKNOWN`，不从“11 项全过”臆造用例归属。无法建立明确判定标准的需求不能计为成功。

**[设计] 需求级结果取值：** `SATISFIED_BY_TESTS / FAILED / UNKNOWN / UNMAPPED`。其中 `SATISFIED_BY_TESTS` 只表示冻结测试支持该需求，不是形式化正确性证明。

需求变更创建新版本，并新建修复任务；不在执行中悄悄改旧任务的需求或测试。首版不支持模型同时修业务代码和验收测试。

**执行状态与工具适用性分层：** 必需构建／测试继续使用已确认计划的 `PASS / FAIL / UNKNOWN / NOT_RUN`，不直接改成五态。可选 `AnalysisObservation` 另有 `applicability = APPLICABLE / NOT_APPLICABLE / UNKNOWN` 与原因：已证实不支持该输入才是不适用；连接失败、未核实语言支持均为未知。不适用不是一次 PASS，不能用于豁免必需门禁。

### 4.4 “可信”的适当含义

**[设计] 首版能做到：** 测试不由补丁随意改写；模型不能自行宣布通过；未知结果不放行；检查与候选内容对应；导出与接受版本对应；失败稿保留。

**不能据此宣称：** 任意仓颉程序语义正确、哈希等于可信计算、所有假修复均可识别、原生 Policy 等于完整安全沙箱。

## 5. 架构与依赖

### 5.1 三条路线比较

| 路线 | 做法 | 取舍 |
| --- | --- | --- |
| **A：现有修复内核＋Sympas-Nexus 适配（推荐）** | 保留已实现的 MCP／候选／Policy／验证／导出，补需求与反馈，通过适配接入指定基座 | [设计] 改动集中，容易验证；必须补实际复用证据，不能只换名称 |
| B：整库搬迁旧平台 | 导入旧网关、医疗／CodeArts 流程、技能库及存储 | [推断] 依赖和领域耦合较大，不能由当前仓颉目标合理化；依据 [N1](#n1)[N2](#n2) |
| C：先做完全自主 Agent | 模型自由选择全部工具、命令和修改路径 | [设计] 暂不采用；状态、副作用和失败判断难控制，不能替代工程验证 |

推荐 A。智能性主要体现在**根据需求和真实反馈修改候选**，不体现在“把所有步骤都交给模型决定”。

### 5.2 分层职责

1. **工作台／网关：** 接收用户目标，展示需求卡、阶段与结果；通过应用服务操作任务，不直接写候选目录。
2. **需求与任务服务：** 冻结需求和验证计划，创建任务，控制唯一执行所有者和状态转换。
3. **修复编排器：** 组织上下文，调用模型与 MCP，消费结果，选择重试或停止。
4. **MCP 工程服务：** 解析类型化请求，检查所属任务、基线和摘要，经 Policy 后执行允许动作。
5. **候选与验证层：** 复制基线、应用修改、构建测试、生成差异；不自行代替用户接受。
6. **存储与交付层：** 持久化事件、关联内容文件，汇总需求级结果，导出接受的同版工程。

目标流程图：[交互式路线图](assets/cangjie-repair-route.html)。图展示主要成功路径、修复反馈和策略停止；人工拒绝、中断核查及保留测试隔离以本版正文为准，不把示意图当作完整状态机。它是目标设计，不代表图中需求关联与反馈增强均已实现；图的排版校验也不是产品运行验收。

### 5.3 运行状态与事件：只有一个事实来源

**[设计] 新框架若有经过验证的持久化任务库：** 通过适配器使用它；当前轻量 Store 的必要方法映射过去，先用测试验证，再做一次有版本的历史迁移。

**[设计] 新框架如果只有内存任务或审计索引：** 继续扩展当前 SQLite，网关仅查询／订阅它；不建立另一套“完成”状态。材料如实写明持久化扩展由本项目新增。

对领域层只暴露最少操作：`create_task`、`get_task`、`transition(expected_status, next_status)`、`append_event`、`list_events(after_sequence)`、`append_record`。不要为显得可扩展建立庞大的通用仓储框架。

**[设计] 状态转换与关键事件在同一个 SQLite 事务内写入。** 外部模型请求、编译或打包不能放在长事务内。文件先写临时对象、校验摘要，再发布引用；数据库与文件不能凭空成为一个原子事务，崩溃后缺文件的记录必须失效。

若另接 EAT 审计索引，它只作为可重建投影，不反向决定任务通过状态。事件支持页面回放，不表示可以自动重放外部写操作或付费调用。

基座复用范围以可核对的实际来源为准，不为接入再建设一套通用平台或重复状态库。版本与接口未确认时，可以先做不依赖适配的需求／反馈工作，但不得提前宣称已经完成新基座集成。

### 5.4 状态机与权限

**[设计] 需求草稿在任务启动前独立确认，启动后沿用现有主状态：**

`READY → DIAGNOSING → GENERATING → APPLYING → BUILDING → TESTING → REVIEW_PENDING → EXPORTING → DELIVERED`

| 情况 | 下一步 |
| --- | --- |
| 构建或测试可靠失败、预算充足 | 构造完整反馈，回到 `GENERATING`；构建失败时测试为 `NOT_RUN` |
| 三候选耗尽，或重复候选／重复失败 | `UNREPAIRED`，保留所有候选，不自动导出 |
| SDK／Policy 缺失，日志不完整，必需检查未知 | `BLOCKED`，提示可操作原因 |
| 已发送写操作或付费请求，结果是否完成无法确认 | `IN_DOUBT`，禁止自动重发 |
| 候选越权修改 | `REJECTED`，不物化、不执行 |
| 用户拒绝已验证候选 | 记录 `decision_source=USER`、拒绝人和原因，任务进入 `REJECTED`；不因拒绝自动发起新的付费调用 |
| 用户取消 | 停止后续步骤；结果不明的在途操作另记 `IN_DOUBT`，不能承诺撤销已发生费用 |

`NeedApproval` 不等于放行或普通失败：等待当前动作的有效批准后才能继续。首版只开放已设计的用户审阅／导出审批；其他动作需要但尚未实现审批入口时停止并说明，不临时把审批接口交给模型。

一个任务只允许一个 worker；启动使用幂等键，状态转换使用预期状态比较。MCP 请求记录结合 `request_id + input_tree_hash + tool_version` 核对，另存参数摘要；已完成的相同请求返回同结果，相同 ID 携带不同参数则拒绝。在途状态不能猜测成功。这里只要求不盲目重放，不承诺未经验证的 exactly-once。

## 6. 关键业务路径

### 6.1 从需求到首次候选

1. 用户选择登记工程；环境预检显示是否可运行，但不因打开页面而调用模型。
2. 需求服务生成模板草稿，用户确认业务条件与修改范围。
3. 固定源码基线、需求版本、验证计划、工具链标识，创建新任务。
4. 经 MCP 取得基线构建／测试诊断；基线业务测试失败是修复输入，环境未知才阻断。
5. 按维护者冻结的可见性规则读取业务源码、必要的本地依赖和公开测试约定；只有全部属于允许公开上下文时，才可读取小工程中的全部 `.cj`。不声称已具备完整语义依赖分析。
6. 向模型提供目标、需求 ID、允许修改路径、源码摘要、诊断和输出契约。
7. 校验模型 JSON、需求引用和路径，交给 MCP `candidate.apply`，由服务端再次执行权限与版本检查。

**上下文可见性规则：** 登记 profile 区分 `PRODUCTION / PUBLIC_TEST / VERIFICATION_ONLY`。前两类可以按任务范围进入生成上下文，第三类用于验证侧保留测试，不向生成模型提供源码或隐藏答案。可见性来自可信登记信息，不接受模型参数覆盖；MCP 读取、搜索、分析结果和上下文组装都要遵循同一限制，不能仅在最终提示词里删除后仍允许工具读回。

首版主案例可以使用公开的冻结测试，不以另建隐藏测试平台为前置。一旦开展独立保留测试评估，就必须先落实隔离，并预先约定可反馈的信息粒度；完整保留测试源码、预期答案和未获准公开的报告片段不能随失败反馈泄漏。

### 6.2 失败后怎样修下一稿

**[事实] 当前循环把失败检查追加进上下文，但没有附带上一稿的修改内容，源码上下文仍源自基线。[S3](#s3)**

**[设计] 新反馈包必须包含：** 上一候选 ID 与树摘要、相对基线的 diff、修改文件的候选内容、编译／测试失败摘要与必要日志片段、对应需求、剩余预算。日志片段先经过上下文可见性检查；保留测试按预先允许的粒度反馈失败类别或位置，而不是直接发送隐藏答案。

首版保留现有的**每稿从同一冻结基线独立生成**语义：下一稿仍返回完整文件替换，`before_hash` 对应基线，不对应上一稿。上一稿只作为修正依据，不能混用两个版本的行号和摘要。

对过长日志按诊断区间截取并记录截取范围；对过大上下文先缩减可选内容或要求用户缩小范围，不能悄悄删掉必需需求。可设置 256 KiB 的应用层上下文字节上限；它不是模型上下文 token 容量承诺。

失败去重保留真实错误位置和用例名，仅去掉时间、ANSI 颜色、候选临时路径等无关差异。重复失败连续两次即停止，避免继续消耗 token。

### 6.3 什么条件才允许进入审阅与导出

**[设计] 自动进入“等待审阅”的条件同时包括：**

- 候选修改没有超出已确认范围，冻结测试／配置未变化。
- 真实构建通过；冻结验收与回归套件均执行完成，无失败和必需跳过。
- 每条必需需求有预先登记且实际执行的目标行为测试套件，回归保持项也有对应结果；固定套件级映射即可，不要求通用逐用例自动发现。必需验收没有 `UNKNOWN / UNMAPPED`。
- 检查绑定同一候选内容、需求版本和验证计划；原始记录可以读取。

人工接受不会把未通过检查改成通过。首版不提供强制绕过。用户可拒绝具体候选；拒绝保留检查和原因，不自动触发下一轮模型请求。确认接受后，导出再次核对接受记录、允许动作、内容摘要与检查集。

交付不是只打包源码。首版归档至少包含以下内容，名称可随实现调整，但语义不能缺失：

| 内容 | 建议归档位置 | 核对要求 |
| --- | --- | --- |
| 被接受的同版本工程源码与冻结测试／配置 | `project/` | 相对工程根的路径映射明确，文件内容与候选清单一致 |
| 相对基线的实际 diff | `evidence/changes.diff` | 由真实文件计算，关联基线和候选摘要 |
| 构建、目标行为、回归报告与未覆盖项 | `evidence/verification.json` | 指向同版检查及完整日志引用，不用一句“通过”替代 |
| 原始需求、确认版本与需求结果索引 | `evidence/requirements.json` | 关联需求 ID、验证计划、测试套件及其结果 |
| 模型／工具原生记录索引 | `evidence/sessions.json` | 记录采集方式、调用 ID、原始记录摘要及可获取位置，缺失项明确标注 |
| 人工评审与接受记录 | `evidence/acceptance.json` | 包含身份、允许动作、有效期、候选／检查绑定和导出消费记录 |
| 摘要清单与支持范围说明 | `manifest.json`、`README.md` | 列清文件集合、排除规则、摘要算法和结果边界 |

`project/` 的工程树摘要与整个 ZIP 的归档摘要分开；证据文件不伪装成参与构建的业务源码。manifest 不自包含自身摘要，其摘要及最终 ZIP 摘要由外部导出记录保存，避免循环定义。

归档内的接受记录保存批准和本次 `export_id` 的预约绑定；最终 `DELIVERED` 状态与归档摘要在成功发布后写入外部导出记录，不为回填状态重写已验 ZIP。失败打包产生的临时文件不得作为交付结果提供。

采集方案在运行前固定：模型 API 原始请求／响应、MCP 客户端与工具返回、真实构建测试日志分别索引。无法取得的工具内部会话标注 `MISSING` 并说明原因，不以自制摘要冒充完整原生记录；必需检查依据或模型调用记录缺失时，不得补造成功链路。

原始模型会话不要求直接塞进源码 ZIP，但引用必须可核对：可采用随交付的脱敏过程材料或维护者有权访问的独立证据包，使用稳定相对引用与摘要，不留下只能在原主机使用的 `/private/tmp/…` 路径。引用的脱敏副本与保留原件分别记录摘要。密钥、`.env`、旧数据库、无关源码和缓存不进入发布包。

### 6.4 “识别假修复”采用分层工程措施

| 退化方式 | 首版措施 | 可作出的结论 |
| --- | --- | --- |
| 删除／改写测试使其变绿 | 路径保护＋基线测试摘要比较＋原生 Policy | 越权修改被拒绝，不等于通用假修复检测 |
| 修了编译错误却破坏业务 | 独立的验收测试＋原有回归 | 该候选未满足冻结约定 |
| 为一个输入写死常量 | 多组合法／边界输入；基于明确业务条件的关系测试 | 能发现所测输入上的退化，不能宣称覆盖全部作弊模式 |
| 只修表层函数，破坏跨文件调用 | 订单入口的组合测试与跨文件回归 | 所测调用链得到验证 |
| 伪造“测试通过”的模型文本 | 忽略模型通过声明，只认固定验证器解析结果 | 模型不能自批 |
| 拿旧日志或其他候选结果充数 | 候选树／需求／计划／检查集关联 | 不匹配结果不能接受或导出 |

例如“合法数量增加 1，总额增加一个单价”的关系，只在数量增加后仍在 1–1000、价格合法且返回值语义不变时成立。关系由维护者确认并冻结，不让修补同一缺陷的模型自行定义自己的合格标准。

推荐展示名称为“退化修复拦截”或“不合格候选拒绝”。评审器输出拒绝原因或待复核，不给未经校准的“假修复概率”。

## 7. 核心模块设计与写作细节

以下每节同时给出开发责任和技术方案书可采用的表述。表述均为目标设计；实施完成后必须补实际文件、测试与运行结果，才能改写成完成时。

### 7.1 M1：基座适配与运行上下文

**职责：** 把仓颉修复作为 Sympas-Nexus 的一个应用能力接入，统一任务 ID、运行状态、事件查询与本机网关，而不是增加第二套平台。

**输入／输出：** 指定框架版本和用户请求 → `RuntimeBinding`（基座版本、外部 run ID、内部 task ID 的稳定映射）。若框架允许直接共享 ID，就不额外增加映射表。

**实现设计：** 新增小型适配器，调用当前 `RepairLoop`。网关只挂载仓颉能力的路由；复用的状态库必须满足条件转换、顺序事件和重启后查询。旧 DAG 只借用依赖表达，不让通用 DAG 再执行一个竞争的修复循环。

**验收：** 通过指定基座网关发起任务，获得的 ID 能查询真实 MCP 调用、候选和结果；页面刷新／进程重启后历史仍可查。至少一项测试使用实际基座，不以 FakeAdapter 代替完成验收。

**方案书写法：** “系统在既有编排与网关之上增加仓颉修复应用层，通过明确的运行上下文和状态适配组织领域流程，避免修改底层框架的无关能力。” 后附复用清单，不用“完全复用”泛称。

### 7.2 M2：工程摄入、需求理解与验收计划

**职责：** 把自由文本目标变成用户确认、后续可检验的约束，同时冻结工程输入。

**接口设计：** `prepare_requirement(project_id, goal) -> draft`；`confirm_requirement(draft_id, edited_spec) -> RequirementSpec`；`build_verification_plan(spec_id, fixture_profile) -> VerificationPlan`。

**实现设计：** 先用订单样例模板和已有用例映射；注册项目时解析 `cjpm.toml`、业务／测试文件、构建根。多构建根由用户选择。文件列表是结构信息，不包装成完整 AST。保留现有尺寸、符号链接和构建脚本限制。

**验收：** 空目标、未知路径、重复需求 ID、未映射必需需求、需求改版都能得到明确处理；已启动任务不会因需求草稿修改而变化。

**方案书写法：** “需求理解的输出不是聊天解释，而是经用户确认的需求条目、修改范围与验收映射；该结构贯穿候选生成和结果评审。”

### 7.3 M3：单编排 Agent 与模型上下文

**职责：** 决定当前阶段允许做什么、何时生成下一稿、何时停止。模型负责候选内容，状态与权限属于控制层。

**输入／输出：** `TaskRecord + RequirementSpec + diagnosis + feedback` → `CandidateProposal`，或明确的停止状态。

**实现设计：** 扩展现有循环，不另起多 Agent。首版固定工具主线；需求模板不调用模型，因此默认最多三个候选请求。可选需求整理最多额外一次，总调用上限四次，并在执行前说明。单次输出上限保留 20,000 tokens，任务总时限保留 480 秒；预算耗尽允许未修复，绝不保证三稿必成。120 秒模型请求与 90 秒构建命令均受剩余总时限约束。

**上下文要求：** 内容均标注来源和版本，源码／注释／README 中的指令一律作为数据。模型不能增添工具权限、改测试计划或回写通过结论。每稿记录实际模型、调用状态和服务返回的 usage；缺少用量不能补写为零。

**验收：** 第一稿通过即停止；可靠失败进入下一稿；重复候选、相同失败、截断 JSON、HTTP 异常、付费请求结果不明均按约定停止。模型替身与 LIVE 结果分开记录。

**方案书写法：** “采用单控制器与模型候选器解耦的有界反馈修复机制，真实工程诊断驱动迭代，固定预算和状态规则限制无效尝试。” 不宣称形式化 CEGIS 全语义保证。

### 7.4 M4：MCP 工程工具与可选分析适配

**职责：** 为读源码、候选操作、构建测试提供标准工具接口；MCP 是协议边界，不是算法名称。

| 保留工具 | 输入要点 | 输出与作用 |
| --- | --- | --- |
| `workspace.list_files` | 基线 ID | 逻辑路径清单，供上下文选取 |
| `workspace.read_file` | 基线 ID、相对路径 | 源码、摘要，供候选生成 |
| `workspace.search` | 基线 ID、字面查询 | 有界文件／行号匹配，供辅助定位 |
| `project.diagnose` | 任务 ID、对象 ID | 构建／测试诊断；可选分析结果单独列出 |
| `candidate.apply` | 结构化修改及请求 ID | 经校验与 Policy 后物化的候选 ID、树摘要 |
| `candidate.diff` | 所属任务的候选 ID | 实际文件差异，用于反馈与审阅 |
| `candidate.build` | 候选 ID、期望树摘要 | 真实构建状态与日志引用 |
| `candidate.test` | 同版候选与先决检查 | 真实测试结果、计数及可解析用例项 |
| `candidate.export` | 候选、接受记录、请求 ID | 同版归档引用与导出 ID |

上述参数是说明重点，不是现有完整 schema；实现以对应输入模型为准。增加需求绑定时由服务端从任务读取，尽量不让模型重复传递可信控制字段。

**课题组工具接入流程：** 确认实际服务地址及工具 schema → 用小型仓颉输入核实支持范围 → 记录输入预处理、输出和错误语义 → 统一为 `AnalysisObservation` → 决定作为可选定位还是发布必需检查。

适用性沿用 4.3 的分层状态。首版必需门禁仍是既定工程工具链；把某个分析工具升级为必需门禁，应另行确认并更新冻结计划，不能在运行中临时增加，或以“不适用”绕开已经确定的必需检查。

当前本地取舍文件记录“服务不可达／仓颉行为未验证”，不能据此断言远端工具绝不支持仓颉。[S10](#s10) 对确需 AST 的工具，只有在仓颉 AST 格式、构建方式和语义边界明确时才接入，不能伪装 C AST。首版不开发新语言前端。

**Agent 选工具的后续设计：** P1 可允许模型提出最多四步的只读 `AnalysisPlan`；服务端只执行白名单内、已验证支持仓颉的工具。写入、执行和导出仍走固定主线，不让模型自由拼命令。没有适用工具时跳过可选分析，不谎称已分析。

**验收：** 经过实际 MCP 会话列工具、读取、搜索、创建候选、构建测试和导出；schema 错误、跨任务引用和断连有明确结果。每项课题组接入提供一份输入／输出小样例，而不是只登记名称。

**方案书写法：** “以 MCP 统一工程能力调用，在工具适用性检查后按需引入课题组分析结果；不以工具注册成功代替程序分析有效性。”

### 7.5 M5：仓颉原生策略与候选工作区

**职责：** 使受限修改真正受执行侧约束；模型建议只能成为候选，不能直接覆盖原工程。

**输入／输出：** 控制层生成的动作、路径、预算、对象与参数摘要 → 原生 `Allow / Deny / NeedApproval` → 可执行动作或拒绝记录。

**实现设计：** 保留 JSONL 与现有 Policy 的职责划分；路径、任务所属关系、基线身份先由 Server 严格校验，原生策略再决定业务动作是否放行。Policy 不可用、超时或响应不匹配都不执行。候选按冻结基线完整复制，在 staging 中校验后发布，差异来自实际文件。

本版 IPC 请求／响应明确带 `schema_version`；请求关联 ID、参数摘要、输入树摘要、动作、剩余预算与审批绑定，响应关联同一请求及决定／原因。策略版本和组件摘要由可信调用侧核对本机实际程序并记录，不能只信模型或进程自报。两端限定 UTF-8 消息长度为 65,536 字节，stdout 只输出结构化响应，诊断写 stderr；不支持的版本或非法字段拒绝。

需求版本和测试计划绑定由服务端检查。新增契约需要同步更新 Python 与仓颉两端并测试，不能假称当前交付程序已经理解新增字段，也不能让旧二进制静默兼容。并非所有约束都必须在仓颉再实现一遍，但原生策略必须实际影响允许／拒绝结果。

可信执行器另外负责解析后的真实文件系统边界、符号链接拒绝、命令白名单、超时和进程组清理；不能用字符串路径前缀检查代替边界验证。独立候选目录不是操作系统沙箱，保留本机受控工程限制，不因此开放任意来源工程执行。

**验收：** 正常业务修改放行；修改测试、配置、越界路径、超预算或缺少策略程序时拒绝；原基线不变。保护演示应区分“直接测原生 Policy”和“经 MCP 端到端拒绝”，两者都不能冒称模型主动产生了恶意补丁。

**方案书写法：** “仓颉承担运行时策略决策，Python 负责请求组织与工程执行；策略决定与动作执行绑定，拒绝不能被编排器旁路。”

### 7.6 M6：工程验证与退化修复评审

**职责：** 对同一个候选回答“能否构建、是否满足所测需求、是否破坏回归”，不只是统计错误数量。

**输入／输出：** 候选内容＋冻结验证计划 → build／test 检查及需求级评审。保留现有 `CangjieVerifier`，增加用例映射与 `assess_requirements(candidate_id) -> ReviewRecord`。

**实现设计：** 构建与测试顺序执行；测试计划由维护者冻结，不接收模型传来的任意命令。测试解析必须符合所锁 SDK 的实际完整输出；零用例、日志截断、跳过必需项、执行环境异常都不能 PASS。编译阶段正常发现的源码错误为 FAIL，与环境 UNKNOWN 分开。

保留既有 `kind=build/test` 和四态；测试结果内增加目标行为、回归两类 `suite_results`，记录其冻结映射和真实结果，不只保存一个总体布尔值。同一次完整 `cjpm test` 可以生成两类结果投影，不为分组添加未经验证的命令参数，也不以单文件编译替代工程验证。无法可靠识别某个必需套件结果时为 UNKNOWN，不按总数猜测。

每次执行保存实际 argv、完整工程根、候选／工具链／验证计划摘要、退出码、有效用例数、跳过与错误计数、完整日志、报告引用、起止或持续时间。反馈可截取必要片段，但完整原始日志应另行保留；缺失数据明确标注，不补成零或成功。

每次评审同时列出 `limitations`，区分不在本次范围内的未检查项、实际检查失败和无法判定项。例如不覆盖整数溢出、并发交错或其他平台时应具体列明；这些范围说明不能被总体绿色状态掩盖，也不允许把必需验收降为未覆盖项。

先对样例冻结足够的业务／回归用例，再验证修复；不在同一任务中根据某个候选“调低”验收标准。对跨文件案例执行工程入口测试，不能只验证修改函数的孤立输出。

**验收：** P0 要求健康基线通过、缺陷基线有可重复失败、正确候选通过，且阶段和未知结果真实。P1 再加入错误语法、可编译常量修复和跨文件退化候选的专项演示。同一案例可使用手写坏候选测试拒绝机制，但必须标明来源，不能算一次 LIVE 修复失败；P1 演示可暂缓，验证器正确区分源码失败与环境未知的要求不能暂缓。

**方案书写法：** “将验证结论分为工程级检查与需求级验收，组合冻结回归、边界输入和适用关系测试，拦截已知类别的退化候选，并保留无法判定的结果。”

### 7.7 M7：事件、结果追溯与交付

**职责：** 保证用户看到的修改、检查的对象和下载的工程相互对应，并能解释失败历史。

**关键关联：** `task → spec → verification_plan → candidate → checks → review → acceptance → export`；模型和工具调用通过任务／候选 ID 连接，不另造一套任务身份。

**实现设计：** 不改写失败记录；摘要只保证内容对应，不替代来源与权限控制。接受记录同时绑定候选、需求、验证计划、检查集、`actor_id`、允许动作和有效期；任一相关内容变化使接受失效。本机单用户场景从服务端会话绑定审批身份，不为此另建多租户身份系统；也不把本地会话标识写成法定身份认证。

**审批消费规则：** 接受仅授权明确的 `candidate.export` 动作。通过数据库唯一约束和短事务将一份审批预约给唯一 `export_id`，记录消费状态；重复点击返回同一预约／已完成导出，不代表再次消费批准。预约后内容或检查发生变化则失效。重试前必须核对操作记录和实际产物；在途状态无法确认时停止，不另起导出掩盖未知结果。

导出按 6.3 的完整清单原子发布，读取时再检查归档摘要。默认 30 分钟有效期沿用现有设计，过期不能原地延期或沿用旧批准。[S5](#s5) 需要重新审阅时必须创建新的有效接受记录；若首版暂不支持已交付任务重新审阅，页面明确提示新建任务，不展示无法完成的“重新审阅”操作。

**启动时的最小中断核查：**

1. 先确认当前运行库的执行所有者，不能把仍由有效 worker 执行的任务误判为中断；所有权无法确认时禁止新的写入并提示人工核查。
2. 查询上次留下的非终态任务及其请求记录。无确认结果的写入、付费调用或导出标记 `IN_DOUBT`，记录 `CONTROLLER_RESTARTED` 原因；可以确定尚未执行的步骤记录 `BLOCKED`／人工待处理原因。
3. 保留已完成候选与检查，允许查询；继续接受／下载前仍核对内容、计划、记录与有效期。已有结果失效时如实显示，不补造缺失记录。
4. 不因启动、刷新或重新订阅事件而调用模型、物化补丁或执行导出；迟到结果只能关联原操作，不能覆盖取消状态或当前候选。不凭不明旧 PID 盲目清理进程。

首版止于识别与人工处置，不提供通用自动续跑；只读查询可受控重试，写操作先对账。人工若要改源码也必须形成新的候选版本，不直接改已验证对象。

**验收：** 改动候选、测试、需求、日志或接受绑定后，旧结果不能继续导出；双击导出只对应一次批准消费和同一导出 ID；拒绝记录具有来源和身份；重启能标记中断任务但不产生副作用；缺失原生记录不被自制摘要冒充。

**方案书写法：** “以需求和源码版本为主线关联执行事件、失败候选与最终归档，实现从结果回看依据的任务级追溯，而不是另建独立审计平台。”

### 7.8 M8：面向用户的工作台

**职责：** 帮用户完成选择、确认、运行、审阅、下载，不把后端内部结构直接展示为产品界面。

**[设计] 页面分四区：**

| 区域 | 默认展示 | 操作 |
| --- | --- | --- |
| 工程与需求 | 工程名、三至五条需求、环境是否就绪 | 选择工程、编辑需求、确认并修复 |
| 任务进度 | 当前阶段、一句可行动错误 | 取消；未就绪时查看缺失项 |
| 修改与验证 | 左右显示 diff、需求／构建／目标行为／回归结果，以及简短未覆盖项 | 切换候选；查看不通过原因 |
| 审阅与历史 | 当前选定候选、是否可接受、历史任务入口 | 接受并导出、拒绝修改、下载；折叠运行记录 |

只在帮助判断时显示计数，比如“回归 11 项通过”；树摘要、JSON、完整路径和工具原始包默认进入折叠技术记录。未覆盖项保留用户能理解的简短提示，细节可展开，不完全藏进技术日志。结论写“必需检查通过”，不写“工程完全正确”。展开控件使用 chevron／文本样式，执行操作用按钮，两者外观区分。

“拒绝修改”是针对当前待审阅候选的执行按钮，与“取消运行”不同；记录可选拒绝原因，拒绝后不能继续导出该候选，也不自动重新付费。若需要再次修复，由用户显式发起新的受控任务。

缺环境时显示“仓颉 SDK 未就绪”，主按钮禁用并提供“查看环境”；缺模型配置时显示“模型未配置”。不要像当前预览那样让用户点击后只收到一整行 `No such file .../cjc`。底层原因保留在日志，不抹掉。

**最小 API 设计：** 保留现有任务／候选／接受／导出路由，新增需求与预检入口；下面是目标契约，不是当前已实现的 API 清单。

| 入口 | 最少输入 | 输出与约束 |
| --- | --- | --- |
| `GET /api/environment` | 无 | 可运行状态、缺失项、友好建议；不返回密钥，不调用模型 |
| `POST /api/requirements/drafts` | 工程 ID、目标文本 | 需求草稿；默认从登记模板生成 |
| `POST /api/requirements/drafts/<id>/confirm` | 用户修改后的需求、草稿版本 | 冻结需求 ID／摘要；旧版本并发确认拒绝 |
| `POST /api/tasks`（扩展） | 工程 ID、冻结需求 ID、幂等键 | 服务端选取冻结验证计划，创建或返回同一任务；不接受客户端自报通过 |
| `GET /api/tasks/<id>`（扩展） | 任务 ID | 用户视图：阶段、需求结果、当前候选、下一步；技术记录按需请求 |
| `POST /api/tasks/<id>/cancel`（新增） | `task_revision` | 取消请求结果和仍可能在途的操作，不伪装为所有副作用已撤销 |
| `POST /api/candidates/<id>/reject`（新增） | `task_revision`、可选原因 | 仅拒绝当前待审阅候选，服务端记录用户身份；不隐式调用模型 |
| `GET /api/tasks/<id>/events?after=<sequence>`（新增） | 事件游标 | 持久化事件增量；轮询先完成，SSE 可后加 |

扩展 `POST /api/tasks` 时必须同步更新页面与请求契约测试：当前入口严格限定字段，不能只在前端塞入 `spec_id` 就认为接通。任务中的 `goal` 从确认需求的原文取得，避免客户端同时提交两份互相冲突的需求。接口错误区分 `ENVIRONMENT_NOT_READY / REQUIREMENT_UNCONFIRMED / CHECKS_NOT_PASS / RESULT_IN_DOUBT` 等业务码，原始异常只放技术记录。

**验收：** 桌面左右区域不出现明显浪费空间；窄屏可上下排列；没有合格候选不能接受；可拒绝当前待审阅候选且随后不能导出；构建、目标行为、回归与未覆盖项可辨；旧异步响应不能覆盖新任务；刷新不重复开始，普通查看／拒绝不会暗中调用模型。

**方案书写法：** “工作台围绕开发者决策展示需求、差异与结果，将执行记录按需展开，在保留可追溯性的同时降低阅读负担。”

## 8. 局部如何支撑整体：推进与验收

### 8.1 优先级与当前可以做的事

### 8.4 评估系统价值，不靠工具数量

系统性对照属于后续评估，不以十二项任务或大规模基准阻塞首版。开展时，两组固定相同任务、基线、模型版本、初始资料和验证侧独立保留测试；明确预算究竟限制 token、调用次数、费用还是总时间，记录实际消耗、超限和结果不明的处理。

主对照采用有合理构建测试能力的轻量修复流程，保留公平预算下的基本反馈／重试能力；每次比较明确改变的机制，例如反馈中是否包含上一稿实际差异，不能同时改变模型、资料和检查标准后把差异归因于系统。若比较需求映射或策略保护，也分别说明相应消融，不能暗中向任一方提供隐藏测试答案。

“一次性模型修改＋真实检查”可以作为低成本参考，单独列出仅一次调用的限制与实际花费，不把它和三候选系统直接称作严格同预算机制对照。所有失败尝试保留，不只挑成功样本；保留测试隔离遵循 6.1 的读／搜／反馈共同边界。

至少记录：任务成功与否、误接受情况、必需需求的所测满足情况、不合格候选被拒绝的原因、候选数、实际模型调用数／token 用量、可核实的模型费用、全部尝试耗时、人工耗时／操作次数和环境阻断数。无法取得费用或用量时标注未知，不按零处理。环境未知不混进代码修复失败，也不从总数中悄悄删除。

可以先做少量案例验证产品价值，但必须标注样本数和支持范围；不凭三个重复订单任务得出普遍修复率或统计显著性结论。
