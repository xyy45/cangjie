# CangSight-Nexus 开发约束：第 6.1 节摘要的工程化解释

日期：2026-10-17  
性质：开发约束与验收依据，不是功能完成报告。本文由用户要求将第 6.1 节的功能理解、技术职责与实现边界整理而成。

## 1. 目标与适用范围

系统面向仓颉工程，完成“需求输入 → 工程上下文 → AI 候选 → 策略决定 → 独立构建测试 → 反馈修复 → 人工审阅 → 同版本导出”的闭环。

核心价值是让修复过程受到约束、结果经过实际验证、交付版本可以核对。不能把模型输出、编译成功或有限测试通过单独解释为修复正确。

本文解释并约束实现方式，不自动启动开发、医疗应用 Autopilot、发布或部署。仅新增本文，不表示产品能力已经存在。

### 文档优先级

1. 用户最新明确指令与适用的项目规则。
2. [当前开发计划](superpowers/plans/2026-10-17-mcp-cangjie-delivery-plan.md)所记录的已确认范围。
3. 本文的职责边界、结果判定与证据要求。
4. 比赛参考摘要与历史设计中的长期目标。

本文不恢复当前计划已取消的门槛。若后续发现冲突，应指出具体条目并按上述优先级处理，不静默扩大范围。

## 3. 功能与技术职责

| 功能 | 必须解决的问题 | 技术与实现方向 |
| --- | --- | --- |
| 需求理解 | 将原文变成可检查的目标，保留原文关联 | Python、结构化 TaskSpec、JSON Schema |
| 流程编排 | 明确阶段、预算、允许动作与停止原因 | Python 单编排器、显式状态机 |
| 工程上下文 | 给模型提供本工程相关源码与真实诊断 | MCP 受限读取、搜索、词法索引；适用的分析工具 |
| 候选生成 | 输出待验证的修改内容 | 模型 API、严格结构化 edits、上下文预算 |
| 策略决定 | 处理工具许可、操作范围和审批条件 | 仓颉原生策略进程、JSONL IPC |
| 受控执行 | 强制执行权限，创建候选并运行固定命令 | MCP Server、可信 Python 执行器、路径校验与进程控制 |
| 工程验证 | 从真实构建和测试得出结果 | 固定仓颉 SDK、`cjpm build -V`、`cjpm test` |
| 人工审阅 | 让人判断具体候选是否接受 | Flask/Jinja、diff、测试报告、审批接口 |
| 证据关联 | 找到需求、候选、测试与交付的对应关系 | SQLite、文件日志、原生会话索引、SHA-256 |
| 效果评估 | 比较修复效果、耗时和成本 | Python 评测脚本、保留测试、JSON/CSV 原始记录 |

依赖和 SDK 的准确版本在环境验证后固定，本文不指定未经验证的版本。旧项目依赖清单不能直接当作新工程锁文件。无需为展示技术数量增加向量库、消息队列、微服务或完整 IDE。

## 4. 需求与上下文约束

- 每项需求保存原文及可观察验收行为，分配稳定的需求 ID。
- 明确输入、预期输出、需要保持的原有行为和本次不覆盖的条件。
- 先执行基线诊断，保存修复前的可重复失败证据；无法建立明确判定标准时，不计为修复成功。
- 上下文来自当前工程、当前候选、真实诊断及明确版本的必要语言资料，记录实际引用。
- 模型不能更换任务根目录、自行授予权限、修改预算或声明审批完成。
- 首版可采用词法检索。正则和词法索引不能宣称为完整 AST 或调用图分析。
- 辅助分析工具只有实际支持仓颉时才接入；不适用时说明原因，不伪造结果，不阻塞固定工具链验证。

示例验收：空订单列表返回 0，正常订单结果保持不变。修复候选应分别关联空列表行为测试和正常输入回归测试，不能只写“解决崩溃”。

## 5. 仓颉策略核与执行边界

仓颉必须实际参与运行时决定，输出 `Allow`、`Deny` 或 `NeedApproval`，附可解释原因。仅保留仓颉源码、注释或演示打印不满足要求。

执行链必须是：

```text
模型建议 → 控制层校验 → 真实 MCP 请求 → Server 校验
        → 仓颉策略决定 → 可信执行器 → 实际工具
```

- 未知工具默认拒绝；越界、预算耗尽、无效或过期审批不能放行。
- 路径、审批状态和剩余预算由可信控制层核验，不能采用模型自报值。
- JSONL 协议限定长度、字段和版本；stdout 只输出结构化响应，诊断写 stderr。
- 策略进程崩溃、超时、响应超长或协议不兼容时，拒绝本次动作并显示原因。
- 仓颉策略不可被旁路；执行器必须消费与当前请求绑定的决定。
- 执行器负责路径规范化、符号链接与越界防护、命令白名单、超时和进程生命周期控制。不能用字符串前缀检查代替文件系统边界校验。
- 模型不能获得任意 shell、密钥、审批接口或发布权限。
- 策略决定与操作系统隔离分别验证；构建脚本和测试本身可能执行代码，独立候选目录不是安全隔离。

## 6. 候选生成与单写者约束

- 模型输出是候选建议，采用严格结构化 edits；用于展示和交付的 diff 由可信层根据实际文件生成。
- 每个候选从冻结的同一基线创建，保留候选 ID、基线摘要、模型与会话引用、修改文件及需求映射。
- 原始工程保持不变。模型不能修改测试、依赖配置、平台配置、SDK 或策略规则来换取通过。
- 补丁物化前检查文件路径、前置内容摘要、允许文件类型、文件数量和修改大小。
- 同一候选只允许一个受控写入者；模型建议、人工操作和重试都必须经过相同入口。
- 验证时冻结候选。内容变化后，原验证结果与接受记录失效，必须重新验证和审阅。
- 若允许后续人工改代码，也必须形成新的候选版本并记录真实贡献，不静默修改已验证候选。
- 不跨任务复用未说明来源的候选、测试报告或会话。

## 7. 独立验证与反馈约束

“独立”指结果由真实工具执行和预先确定的判定规则产生，生成模型不能自行将检查设为通过；首版不要求另建分布式验证服务。

### 固定环境

- 记录 SDK 版本、平台、安装包来源及 SHA-256、实际工具版本与依赖锁文件。
- 固定完整工程构建根，通过 MCP 调用白名单命令 `cjpm build -V`、`cjpm test`。
- 禁止通过单文件临时编译代替工程验证；禁止使用未经固定 SDK 验证的参数。

### 结果判定

| 状态 | 含义 |
| --- | --- |
| PASS | 实际执行完成，结果满足预先确定的检查标准 |
| FAIL | 实际执行得到明确不满足要求的证据 |
| UNKNOWN | 环境、超时、协议或报告异常导致无法可靠判定 |
| NOT_RUN | 尚未执行，不能算通过 |
| NOT_APPLICABLE | 有明确理由不适用；不能用于跳过必需门禁 |

- 分别记录构建、目标行为测试和回归测试，不用一个布尔值隐藏阶段差异。
- 保存命令参数、候选摘要、工具链摘要、退出码、有效用例数、跳过情况、完整日志、报告及耗时。
- 零测试、全部跳过、空响应、旧报告或不完整日志不能仅凭退出码 0 判为通过。
- 必需检查全部通过后才能进入接受流程；编译通过不等于行为正确，测试通过不等于普遍正确。
- 可归因的代码失败且预算仍有剩余时，将真实诊断反馈给模型生成下一候选；环境错误停止并说明原因。
- 重复候选、超出三个候选预算、取消和超时都应有明确终态，不无限迭代。

## 8. 人工审阅与交付约束

审阅页面至少展示需求、实际 diff、构建结果、测试结果、未覆盖项和停止原因，并支持接受或拒绝具体候选。

- 审批绑定候选摘要、允许动作、有效期和审批身份；不能只记录“某任务已同意”。
- 批准后内容变化，旧批准无效；一次性操作不能重复消费同一批准。
- 导出前核对当前树摘要与被验证、被接受的摘要一致；不一致则阻止导出。
- 交付包含同版本源码、相对基线 diff、验证报告、需求与结果索引、会话引用、接受记录和摘要清单。
- 不将密钥、`.env`、旧数据库、无关用户源码或缓存加入发布包。
- 原生记录的采集方式必须事先明确。无法取得的工具内部记录标注缺失；自制摘要不能冒充完整原生会话。

## 9. 数据契约、记录与内容摘要

所有对象使用明确版本；可信控制层生成身份 ID，模型只能提交建议内容。首版至少表达以下逻辑对象，允许在实现中合并存储，不要求为每项建立独立服务。

| 对象 | 最少需要表达的信息 |
| --- | --- |
| TaskSpec | schema_version、任务 ID、基线引用、需求、允许范围、工具和预算 |
| ToolRequest | 请求 ID、任务与候选 ID、工具名、参数、输入树摘要、截止时间 |
| PolicyDecision | 请求绑定值、策略版本与组件摘要、决定、原因、审批绑定值 |
| Candidate | 基线摘要、文件前置摘要、修改内容与 diff 摘要、模型及会话引用 |
| CheckResult | 阶段、状态、候选与工具链摘要、退出码、用例统计、报告引用、耗时 |
| RunEvent | 顺序号、关联 ID、时间、事件类型、输入输出与产物引用 |
| Acceptance/Export | 接受的候选摘要、审批与导出状态、最终清单摘要 |

未知版本和非法字段必须明确拒绝或按已经定义的兼容规则处理，不能静默猜测。

最终树摘要按明确文件集合生成：规范化相对路径，计算文件内容摘要，按路径排序，再对规范化清单计算总摘要。记录纳入和排除规则；涉及执行语义的文件类型与权限元数据应有明确处理规则。

需求、原生会话、diff、验证报告、人工接受和交付都关联到同一候选版本。SHA-256 用于内容核对，不能单独证明正确性、作者身份或记录不可篡改；首版不宣称数字签名或不可抵赖证据链。

## 10. 恢复与副作用去重

持久化、自动恢复和副作用去重是三件不同的事，必须分开描述。

首版要求：

- 任务、候选和已完成结果落盘；页面刷新不能重复创建任务或再次发起付费调用。
- 重启后能够识别中断任务，并标记需要人工处置；不宣称完整自动恢复。
- 未知在途的写操作或付费调用不自动重放，迟到结果不能覆盖已取消任务或当前候选。
- 只读操作可以受控重试；写操作在重试前查询执行记录并核对实际产物。
- 可使用 `request_id + input_tree_hash + tool_version` 组成幂等键，并以唯一约束和受控状态转换防止重复执行。
- 文件修改和数据库事务不是天然原子的；“文件已改但结果未入库”的中断必须核验实际状态，无法确认时停止并提示人工处理。
- SSE 只推送事件，不能因重新订阅而再次应用补丁或执行导出。

后续自动恢复需增加检查点核验、执行状态对账与明确重试规则。未验证这些能力前，不承诺 exactly-once 或任意中断后自动续跑。

## 11. 对照评估与结论边界

首版先完成可信主案例和拒绝演示。摘要中的系统性对照评测是后续目标，不以未完成的十二任务阻塞当前主链，也不在材料中提前声称完成。

开展对照时应满足：

- 两组使用相同模型版本、任务、基线、初始资料与独立保留测试。
- 明确定义预算是 token、费用、调用次数还是时间，记录实际消耗及超限处理。
- 轻量基线应具有合理的基本构建测试能力；明确比较中改变的机制，避免使用刻意削弱的对照。
- 保留测试由可信验证侧维护，不允许模型修改，不把隐藏答案直接提供给生成流程。
- 报告修复成功率、误接受、全部尝试耗时、模型费用、人工耗时及失败原因；小样本列出原始结果，不夸大统计意义。
- 无明确判定标准的任务不计成功；单案例演示不能推出通用修复能力。

每次结果明确列出尚未覆盖的语义或环境，例如整数溢出、并发交错、大输入、平台差异。分别标注未检查、检查失败和无法判定，不能用一个绿色状态掩盖限制。
